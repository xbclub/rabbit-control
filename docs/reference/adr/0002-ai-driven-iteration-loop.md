# ADR-0002: AI 驱动开发下的语言选型修订

- 状态：提议（修订 ADR-0001 第 5、6 节）
- 日期：2026-11-19
- 背景：项目确定由 AI 承担全部编码工作，无人工手写代码。团队规模与「语言熟练度」约束失效，取而代之的约束是 **AI 的迭代回路效率**。
- 相关：[ADR-0001 语言选型](./0001-language-choice.md)

## 1. 前提变化带来的三点修正

### 修正一：ADR-0001 中的「团队画像」决策表作废

原表用「团队是否熟悉 Rust」作为主判据。AI 对两种语言都熟悉，因此该判据失效。新的主判据变为：

1. **每次改动的反馈延迟**（编译 + 测试 + 检查）
2. **AI 单次通过率**（写完就对的概率，决定迭代次数）
3. **失败时的可诊断性**（错误信息是否指向具体位置、能否被 AI 自行修复）

### 修正二：「混合架构需要 ≥3 人」的限制放宽，但不取消

AI 没有上下文切换成本，双语言的心理负担消失。但跨语言边界的 **API 契约设计** 仍然需要人类决策，且 AI 在两种语言之间「脑内翻译」时容易在序列化、内存所有权、错误映射上出错。结论：混合架构从「禁止」放宽为「可行，但边界必须窄且接口必须极简」。

### 修正三：「开发效率」的权重上升

原 ADR 认为「总工作量持平，只是风险位置不同」。在 AI 主导编码的假设下，这个结论需要修正：**总工作量仍然基本持平，但「反馈延迟」对 AI 的实际产出速度是乘性影响，不是加性影响。** 编译等待 3 分钟 vs 8 秒，差的不是一个常数，而是 AI 在每个任务上能试错的轮次。

因此：**迭代回路效率必须作为一等决策指标**，这一点用户的直觉是对的。

## 2. Rust 慢在哪里（可量化，且大部分可修）

关键判断：**Rust 的慢主要不是语言复杂度，而是工程配置与依赖结构。** 大部分痛点可在 1–2 天内消除。

| 痛点 | 根因 | 缓解手段 | 预期效果 |
|---|---|---|---|
| 增量编译慢 | 单 crate 巨大 + 泛型单态化爆炸 | 拆成 8–15 个小 crate，叶子 crate 依赖少 | 增量编译从分钟级降到秒级 |
| 链接慢 | 默认链接器慢 | macOS `lld`/`zld`，Linux `mold`，Windows `lld-link` | 链接时间降 50–80% |
| 测试慢 | `cargo test` 编译整包 + 串行 | `cargo nextest`（并发执行）、只测受影响 crate | 提效 3–10× |
| 内循环慢 | 每次都 `cargo build` | 内循环用 `cargo check`（不做 codegen/link） | 快 3–10× |
| 过程宏开销 | `serde`/`tokio`/`thiserror` 等宏 crate 反复编译 | 依赖分层隔离、`sccache` 缓存 | 首次构建显著下降 |
| 调试构建慢 | dev profile 默认 `opt-level=0` 但仍在跑 codegen | 依赖用 `opt-level=2`、自身用 `0`（见下） | 运行时与构建双赢 |
| 磁盘占用大 | `target/` 积累增量产物 + 多 profile | 定期 `cargo sweep`、CI 独立 `CARGO_TARGET_DIR`、`split-debuginfo` | 从 20–40GB 降到 5–10GB |

推荐的 `Cargo.toml` 开发配置：

```toml
[profile.dev]
opt-level = 0
debug = 1              # 只保留行号，不做完整 DWARF

[profile.dev.package."*"]
opt-level = 2          # 依赖优化编译一次，之后不再重编

[profile.test]
opt-level = 0
```

配套：`RUSTFLAGS="-C link-arg=-fuse-ld=lld"`（Linux/Windows）、macOS 用 `-C link-arg=-fuse-ld=lld` 或 `zld`。
值得注意：**这些配置带来的提升是可验证的，应当在第一个 Spike 里实测，而不是凭感觉判断。**

### 但有一类慢是无法消除的

- **Borrow checker 的往返**：涉及 `tokio` 异步 + FFI 借用 + 跨线程共享帧缓冲时，错误信息长、修复路径不唯一，AI 容易反复试错。这是 Rust 对 AI 最不友好的地方，占比通常是编译时间的数倍。
- **特性编译（feature unification）**：大依赖树里改一个 feature 会触发上游重编。

这两类只能靠 **架构上主动规避**：把 FFI 边界收窄成极小的 unsafe 模块，把状态集中到少量「拥有者」结构体，避免在异步代码里传递大量借用。

## 3. Go 的真实收益与隐藏成本

### 收益（对 AI 迭代回路）

| 项 | 说明 |
|---|---|
| 编译速度 | 小项目 `go build` 亚秒级，中型项目数秒；无单态化 |
| 测试速度 | `go test` 缓存命中后近乎瞬时 |
| 磁盘占用 | module cache + build cache 通常 <2GB |
| 语言表面小 | 无生命周期、无 trait 求解、无宏，AI 单次通过率更高 |
| 错误信息 | 极简，且几乎总是「错在哪一行」 |
| 生态统一 | `gofmt`/`go vet`/`go test` 一套标准，AI 不需要在多个工具间切换 |

**这些收益是真实的，且正好命中用户描述的三个痛点：写得慢、编得慢、占硬盘。**

### 隐藏成本（对 AI 尤其致命）

| 项 | 说明 |
|---|---|
| **cgo 段错误不可诊断** | Windows COM / DXGI 写错一个 vtable 偏移 → 进程直接段错误，无 Rust 那种类型错误、无清晰 panic 位置、无栈回溯质量。**AI 修复段错误的能力远弱于修复编译错误**，一次这样的排查可能吃掉一周 |
| 采集层无可复用件 | Go 生态只有 GDI/X11 轮询式截图（`kbinani/screenshot`），DXGI Desktop Duplication、ScreenCaptureKit、PipeWire 都需自写绑定 |
| 硬件编码绑定 | 只能 cgo；NVENC/VideoToolbox/VAAPI 的 Go 封装极不成熟 |
| 零拷贝缺失 | 帧缓冲跨 cgo 边界需要 `C.malloc` + 手工生命周期，或 Go 内存固定，容易泄漏或悬垂 |
| 帧率相关的底层调优 | 线程亲和性、优先级、NUMA、`mlock`、实时调度在 Go runtime 下不可控（GC 会抢占、GOMAXPROCS 干预） |

### 关键判断

> **Go 省下的是「编译时间」，可能用「运行时崩溃排查时间」偿还。**
> 对一个以「低延迟、高帧率」为唯一卖点的项目，媒体管线里 30% 的代码是 FFI，而这 30% 恰好是 AI 最难自愈的部分。

若把这个产品降级成「能用就行」的远程工具，Go 是最优解。但目标是**在帧率与延迟上打赢 RustDesk**，就必须对编码器、采集器、调度器有细粒度控制——这部分 Go 做不到。

## 4. 三种可行方案（修订版）

### 方案 A'：纯 Rust + 强制工程提速（推荐）

保留 ADR-0001 的方案 A，但把「迭代回路优化」作为**第一个里程碑的交付物**，而非事后优化。

- 必须交付：拆分 crate、`cargo check` 内循环脚本、`nextest`、`mold`/`lld`、`sccache`、`cargo sweep` 清理任务
- 验收标准：**单文件改动的 `cargo check` ≤ 3s，`cargo nextest` ≤ 15s，`target/` ≤ 10GB**
- 若达不到上述指标，则触发方案 B' 重评估（这是可证伪的决策点）

### 方案 B'：纯 Go + FFmpeg 子进程承担媒体层

**这是 Go 路线唯一值得认真考虑的形态。**

架构：Go 主进程负责会话、信令、输入注入、UI 桥接；采集与编码由 **FFmpeg 子进程** 完成（Windows `ddagrab` + `h264_nvenc/qsv/amf`，Linux `kmsgrab`/`x11grab` + `vaapi`，macOS `avfoundation` + `h264_videotoolbox`），Go 通过管道读取 Annex-B 码流，再经 `pion/webrtc` 或自研 QUIC 发送。

- 优势：**完全避开 cgo/COM**，AI 只需处理进程管理与字节流；迭代回路最快
- 代价：
  - 延迟下限抬高（进程管道 + FFmpeg 缓冲，调优后可到 30–60ms，但很难进入 15ms 级别）
  - 无法按帧精确控制码控、无法在编码器内部做 ROI/脏区提示、强制关键帧只能靠信号
  - 进程生命周期、崩溃恢复、权限（macOS 屏幕录制授权）都要额外处理
- 适用条件：目标 SLO 是「1080p30 / 端到端 ≤60ms」，而非「4K60 / ≤20ms」

### 方案 C'：Go 服务端 + Rust 客户端（混合，修订允许）

ADR-0001 中「<3 人禁止混合」的限制在 AI 主导下可放宽为「**边界必须窄**」：

- 服务端（rendezvous / relay / API / 鉴权 / 管理）：Go，享受快速迭代
- 客户端（采集→编码→调度→传输→解码→注入）：Rust
- 唯一跨语言边界：**线协议（protobuf/flatbuffers）+ HTTP/JSON 管理接口**，绝不共享内存或 FFI
- 风险：AI 在两侧同时改动时容易让协议版本漂移 → 用 protobuf 单一真源 + 契约测试锁死

## 5. 决策规则（修订）

| 情形 | 选择 |
|---|---|
| 可以接受 1080p30 / 端到端 60ms 级 | **B' 纯 Go + FFmpeg 子进程**（迭代最快，AI 最省心） |
| 要求 1080p60+ / 4K / 端到端 ≤30ms | **A' 纯 Rust**，且必须先完成工程提速并把指标写进里程碑 |
| 要求极致指标 + 想要 Go 的开发速度 | **C' 混合**，但要接受协议边界的一致性维护成本 |

## 6. 决定性实验（2 天，必须先做）

不要靠感觉选语言。用同一个最小功能做 A/B：

**测试用例**：Windows 端采集屏幕 → H.264 硬编 → 本地回环解码显示，统计 1080p60 下的端到端延迟。

| 组 | 实现 |
|---|---|
| A | Rust：`windows` crate + DXGI Desktop Duplication + `ffmpeg-next` NVENC |
| B | Go：`ddagrab` FFmpeg 子进程 + `pion` 读流 |

测量并记录：

1. **AI 迭代回路**：从「改一行代码」到「看到测试结果」的墙钟时间（中位数，取 20 次）
2. **首次跑通所需轮次**：AI 尝试次数、遇到的错误类别（编译错 / 段错误 / 逻辑错）
3. **端到端延迟与稳定帧率**（P50 / P99）
4. **磁盘占用与冷启动构建时间**

第 1、2 项决定开发速度，第 3 项决定产品能否成立。**如果 B 组的延迟不达标，则无论迭代多快都不选 B。**

## 7. 当前结论

1. **「换 Go 能提升帧率」——不成立，与 ADR-0001 结论一致。**
2. **「换 Go 能提升 AI 迭代速度」——成立，且幅度可观**（编译/测试/磁盘三项都是数量级差异）。
3. **但 Go 把这个速度优势抵押在了 cgo 段错误的排查上**，而这正是 AI 最弱的能力。
4. 因此：**先花 1–2 天做第 6 节的实验**。若 Rust 能做到 `cargo check ≤3s / nextest ≤15s`，则 A' 的迭代痛点基本消失，直接选 A'；若做不到且能接受 60ms 级延迟，选 B'。

**不建议在未做实验前凭「Rust 编译慢」这一条感受直接切换语言**——这个感受是真实的，但它对应的是可以由配置解决的那部分问题。
