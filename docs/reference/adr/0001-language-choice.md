# ADR-0001: 客户端与服务端的语言选型（Rust vs Go）

- 状态：提议（待决策）
- 日期：2026-11-19
- 决策人：项目负责人
- 相关：[02 架构与媒体管线](../design/02-architecture.md)、[07 工程提速](../design/07-engineering-velocity.md)

## 1. 背景与问题陈述

目标产品是类 RustDesk 的远程桌面控制软件，核心卖点是**解决 RustDesk「帧率上限高、实际帧率低」的痛点**。

当前纠结点：是否把技术栈从 Rust 换成 Go，以换取更高的开发效率。

## 2. 关键澄清：语言不是帧率问题的原因

**换成 Go 不会提升实际帧率，一行也不会。** 实际 FPS 低是架构问题，与语言无关。需要逐层测量定位，典型瓶颈链如下（按出现概率排序，需用数据验证而非假设）：

| # | 瓶颈 | 现象 | 归属 |
|---|---|---|---|
| 1 | 采集路径是「全帧轮询」而非「脏区/损坏驱动」 | 静止画面也满负荷，动起来就掉帧 | 架构 |
| 2 | 走软件编码（VP8/VP9）而非硬件编码 | 1080p 以上软件编码天花板 15–30fps | 编码器策略 |
| 3 | 编码器参数为「质量优先」而非「延迟优先」 | 单帧编码耗时 30ms+，60fps 无望 | 编码器策略 |
| 4 | 传输层无 pacing、无 FEC、或走 TCP | 丢包触发重传 → 队头阻塞 → 画面冻结 | 传输 |
| 5 | 帧调度器缺失：不做 deadline-aware 丢弃 | 编码队列堆积，延迟越滚越大，表现为低帧率 | 架构 |
| 6 | 单线程管线 + 锁竞争 | CPU 多核利用率低，单核打满 | 实现 |

**结论**：真正的护城河是「采集→编码→调速→传输」这条媒体管线。选语言时，应该问的是「哪种语言更容易把这条管线做对、做快、做到三平台」，而不是「哪种语言开发效率高」。

## 3. 候选方案对比

### 3.1 与「媒体管线」相关的硬指标

| 关注点 | Rust | Go | 判定 |
|---|---|---|---|
| 屏幕采集生态 | `scap`、`xcap`、`windows-rs`、`core-graphics` 等成熟 crate | 仅 `kbinani/screenshot`（GDI/X11 轮询，性能差），DXGI/ScreenCaptureKit 需自写绑定 | **Rust 显著优** |
| Windows COM/DXGI 集成 | `windows-rs` 提供类型安全的 COM 封装 | `golang.org/x/sys/windows` 裸 syscall，COM 需手写 vtable | **Rust 显著优** |
| 硬件编码绑定 | `ffmpeg-next`、`nvenc`、`videotoolbox`、`openh264` 均有可用封装，FFI 零成本指针传递 | 只能 cgo；跨边界传大 buffer 需固定内存、回调需 handle 间接层 | **Rust 优（开发体验）** |
| 实时内存管理 | 零拷贝 bufffer 生命周期由所有权表达，无 GC | 需靠 `sync.Pool` + 手工规避逃逸，否则 8MB×60fps 产生 GC 压力 | **Rust 优** |
| 传输 / 拥塞控制 / FEC / NACK | `quinn`(QUIC)、`str0m`、`webrtc-rs`（成熟度递减） | **`pion/webrtc` 是两个生态中最成熟的实时传输库**，自带 GCC 拥塞控制、NACK、PLI、FEC、jitter buffer | **Go 显著优** |
| 服务端并发（信令/中继/鉴权/管理） | tokio 可行但样板多 | goroutine 模型天然匹配，开发与运维体验最佳 | **Go 显著优** |
| UI 外壳 | Tauri（成熟）、egui、slint | Wails（webview）、Fyne（本场景不适用） | Rust 略优 |

### 3.2 需要澄清的两个常见误解

**误解一：「Go 有 GC，做不了 60fps 实时管线」**
错误。Go 的 GC 停顿在毫秒以下，配合 `sync.Pool` 复用帧缓冲后完全可用。真实代价是要「知道要这么做」，而不是「做不到」。

**误解二：「cgo 每帧跨界调用开销大，拖累帧率」**
错误。指针传递到 C 是零成本的，每次调用约百纳秒量级，60fps 下可忽略。cgo 的真实成本是**开发期摩擦**：COM 样板、回调、内存固定规则，属于工程效率问题，不是运行时性能问题。

## 4. 方案与决策

### 方案 A：纯 Rust（推荐作为主方案）

- 优势：媒体管线生态完整；三平台硬件编码与采集绑定齐全；无 GC 抖动；长期维护成本最低；与用户原有的 Rust 技术积累和技能栈一致。
- 劣势：服务端（信令、中继、鉴权、后台）开发速度明显慢于 Go；团队若不是 Rust 熟练工，首版周期会被 borrow checker 拖长。

### 方案 B：纯 Go

- 优势：**仅当团队 Go 熟练、且必须 3 个月内出可用 Demo 时成立**。`pion/webrtc` 能一次性买到拥塞控制、FEC、NACK、jitter buffer——恰好是修复帧率问题的传输层基建，这是极强的先发优势。
- 劣势：采集与硬编绑定要自己写，Windows 上 COM 工作量被严重低估；三平台客户端质量风险集中在你最不擅长的地方。

### 方案 C：混合 —— Go 服务端 + Rust 客户端（长期最优）

- 服务端：rendezvous / relay / API / 鉴权 / 管理后台 → Go
- 客户端：采集 → 编码 → 调度 → 传输 → 解码 → 呈现 → 输入注入 → Rust
- 前提：团队 ≥3 人，且有能同时 cover 两种语言的人；否则两种语言各自的少量人力都会变成瓶颈。

## 5. 决策规则（按团队画像选择）

| 团队画像 | 推荐方案 | 理由 |
|---|---|---|
| Rust 为主，长期投入，追求产品级质量 | **A 纯 Rust** | 护城河在媒体管线，别把它放在团队最不熟练的语言里 |
| Go 为主，需快速验证产品方向 | **B 纯 Go + pion** | 用 pion 换取传输层成熟度，接受客户端后期返工成本 |
| 双语言能力，≥3 人，12 个月以上周期 | **C 混合** | 各取所长，长期总成本最低 |
| 团队 <3 人 | **不允许 C**；在 A / B 中按主语言选 | 双语言在小团队中必然导致两套半成品 |

## 6. 对「开发效率」的量化判断

- 网络/服务层代码：Go 约快 1.5–2×，且新人上手成本显著更低。
- 采集/编码/OS 集成代码：Go 反而**更慢**，因为要手写绑定与 COM 样板。
- 本项目两者体量大致相当 → **总工作量约为持平**，但风险分布不同：
  - 选 Go = 把风险堆在客户端（产品差异化所在）。
  - 选 Rust = 把风险堆在服务端（可外包、可后补、可用成熟方案兜底）。

## 7. 待验证项（决策前应完成）

1. 对现有 RustDesk 在目标场景（1080p/4K、30/60fps、弱网）做瓶颈归因测量，确认语言并非瓶颈。
2. 用 1 人·周做 Go 侧 DXGI Desktop Duplication + NVENC 的原型，量化 COM/cgo 开发摩擦。
3. 用 1 人·周做 Rust 侧同等原型，对比代码量与首帧延迟。
4. 依据实测结果回填本 ADR 并定稿。

## 8. 默认结论

**若团队有 Rust 基础：维持 Rust（方案 A），并在服务端优先复用现成组件而非自研。**
**若团队是 Go 原生且以速度优先：方案 B 可行，但必须提前接受「客户端采集/硬编自研」这一成本项，且要在任务书中单独立项。**
**任何情况下都不要把「换语言」当作帧率问题的解决方案。**
