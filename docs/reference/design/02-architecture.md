# 02 架构与媒体管线

> **本文档是全项目的核心。** 帧率问题 100% 在这里解决或失败。其他文档都是围绕本文档的支撑。

## 0. 与 RustDesk 对比后的修正（2026-11-20）

我们实际阅读了 RustDesk 源码（见 [ADR-0004](../adr/0004-rustdesk-fork-evaluation.md)），
修正了三条原始归因中的两条。**这直接影响本文档的优先级判断，务必先读这一节。**

### 0.1 修正后的真实差距

| # | 问题 | RustDesk 实际情况 | 我们是否差异化 | 本文档对应章节 |
|---|---|---|---|---|
| 1 | 采集事件驱动 | ✅ 已经做了（DXGI `WouldBlock`） | ❌ **不是优势，是基线** | §2 |
| 2 | 编码参数延迟优先 | ⚠️ 有 quality 比值，但默认偏质量 | ⚠️ 小幅优势（+20~30%） | §3 |
| 3 | **deadline-aware 调度** | ❌ **完全没有** | ✅ **唯一真正的护城河** | §4 |

**因此：本文档 §4（帧调度器）的权重远高于 §2、§3。**
若时间有限，优先把 §4 做对；§2、§3 做到业界标准即可。

### 0.2 六个必须做对的点（每个都对应 RustDesk 的一个具体缺陷）

以下 Q1–Q6 是**硬性要求**，每个对应 RustDesk 源码里一个可定位的缺陷：

| # | 要求 | RustDesk 的反面做法（源码位置） | 差距 |
|---|---|---|---|
| **Q1** | 首帧即目标帧率，无冷启动降级 | `INIT_FPS = 15`，前 1 秒强制 15fps（`video_qos.rs:54,828`） | 4× |
| **Q2** | 帧率判定基于**本地 deadline**，不依赖网络探针周期 | 依赖 1Hz `TestDelay`（`connection.rs:510`） | 延迟感知慢 1 秒 |
| **Q3** | 接收端队列**深度 ≤ 2 帧**，超出立即丢旧帧 | `VIDEO_QUEUE_SIZE = 120`（`client.rs:114`）= 2 秒缓冲 | **60×** |
| **Q4** | 帧率升降**对称**（同一套 deadline 判定） | 上升 `+1`/`+5`，下降做除法（`video_qos.rs:523,546`） | 恢复慢 9 秒+ |
| **Q5** | 捕获无变化**不重复编码** | 重复编码同一帧最多 10 次（`video_service.rs:729,935`） | 10× 浪费 |
| **Q6** | 延迟反馈**扣除队列排队时间** | 自己承认被污染（`video_qos.rs:43-44` 注释） | 测量失真 |

**其中 Q3 单独就足以构成产品差异**：120 帧 vs 2 帧的队列深度，是「画面比现实晚 2 秒」和「晚 33ms」的区别。

**每一个 Q 都必须在对应 crate 的测试里有覆盖**（见各任务卡的「测试清单」）。

### 0.3 不要做的事

- ❌ 不要把「事件驱动采集」当成营销卖点——RustDesk 已有，用户不会因此选择我们
- ❌ 不要试图通过「调编码参数」获得数量级提升——顶多 20–30%
- ✅ 要把「**你看的画面永远是 33ms 前的，不是 2 秒前的**」作为核心叙事

### 1.1 设计原则

| 原则 | 说明 |
|---|---|
| **P1 端到端单一进程完成媒体管线** | 无子进程、无 IPC 拷贝。见 [ADR-0003](../adr/0003-final-rust-decision.md) |
| **P2 事件驱动，禁止固定周期轮询** | 采集由屏幕变化驱动；无变化时 CPU 归零 |
| **P3 延迟优先于画质** | 任何队列满时丢帧，不排队 |
| **P4 丢弃由截止时间决定，不由 FIFO 决定** | 见 §4 Frame Scheduler |
| **P5 输入与控制永不排在媒体之后** | 独立通道 + 独立优先级 |
| **P6 每段可独立测量** | 每个组件都有延迟埋点，可单机回环验证 |
| **P7 任何环节可单机自测** | `loopback` 模式让采集→编码→解码→呈现跑在本机 |

## 2. 采集层（Capture）

### 2.1 核心要求

**这是 RustDesk 帧率问题的第一个源头：全帧轮询。**

绝大多数远程桌面在静止画面时仍在满负荷采集 + 编码。RC 的要求：

| 要求 | 实现 |
|---|---|
| 无事发生时零开销 | 依赖平台事件通知；无事件则不采集 |
| 只传输变化区域（可选） | 脏区分析（Dirty Region），见 §2.3 |
| 帧时间戳准确 | 用系统单调时钟，记录「内容实际变化时刻」而非「采集返回时刻」 |
| 支持自愈 | 分辨率/显示器/HDR/锁屏变化后自动重建捕获 |
| 不阻塞渲染 | 采集在独立线程，与编码解耦 |

### 2.2 平台抽象

```rust
/// 采集源的统一抽象。所有实现必须满足：无变化时不产生 Fn。
pub trait CaptureBackend: Send {
    /// 阻塞等待下一帧，超时返回 None（允许驱动后续逻辑）
    fn next_frame(&mut self, timeout: Duration) -> Result<Option<CapturedFrame>>;
    /// 显示配置变化时返回需要重建
    fn poll_invalidation(&mut self) -> Option<InvalidationReason>;
    fn rebuild(&mut self) -> Result<()>;
}

pub struct CapturedFrame {
    pub texture: FrameTexture,     // 平台相关：DXGI Texture / CVPixelBuffer / dmabuf
    pub timestamp: Instant,        // 内容变化时刻（非采集完成时刻）
    pub dirty: Option<Region>,     // 脏区（若后端支持）
    pub seq: u64,                  // 单调递增
    pub is_repeat: bool,           // 内容与上一帧相同
}

pub enum FrameTexture {
    D3D11(ID3D11Texture2D),
    CVPixelBuffer(CVPixelBufferRef),
    DmaBuf { fd: RawFd, modifier: u64, stride: u32 },
    Cpu(Vec<u8>),                  // 兜底：软件采集
}
```

**关键设计：`FrameTexture` 是零拷贝句柄。** 采集 → 编码 → 编码器直接消费 GPU 纹理，CPU 全程不参与，除非走软件编码兜底。

### 2.3 脏区分析（Dirty Region）—— 可选项，但收益巨大

不是所有场景都用得上，但必须实现：

- **价值**：静态办公场景（打字、看文档）下，脏区通常 <5% 屏幕面积，编码时间与码率可降一个数量级
- **做法**：
  1. 优先用平台原生能力：Windows 有 `IDXGIOutputDuplication::GetFrameDirtyRects` / `GetFrameMoveRects`
  2. macOS 退化：Apple 无脏区 API，需自行做块级（16×16 或 32×32 tile）哈希比对
  3. Linux: PipeWire 无脏区，同 macOS 自行比对
- **编码器侧**：NVENC 支持「按区域编码」（`NV_ENC_PIC_PARAMS::dirtyRects`），但仅 H.264/HEVC 部分驱动支持；不支持的走「整帧编码但降低码率」
- **决策**：脏区信息同时用于（a）降低编码面积（b）降低码率（c）指导关键帧策略

### 2.4 帧率请求与采集频率解耦

> **修正（2026-11-20）**：本节原稿把「定时器采集」列为 RustDesk 的问题。
> 实测源码后发现 RustDesk 的 DXGI 后端已是 `WouldBlock` 事件驱动
> （`libs/scrap/src/common/dxgi.rs:45`），**没有这个缺陷**。
> 因此本节不是「差异化点」，而是**必须达到的基线**——做不到就是退步。

用户的直觉实现：`fps=60` → 采集线程按 1/60s 定时唤醒 → 每 16.7ms 采一帧。

问题：
- 定时器与真实屏幕刷新（可能是 120Hz/144Hz）不同步 → **拍到的帧时间抖动**
- 用户改了窗口内容但采集时刻还没到 → **输入延迟被锁死在 16.7ms**
- 屏幕无变化时也在采 → **CPU 空转**

正确做法：

```
屏幕事件（VSync / 内容变化通知）
        │
        ▼
   立即采集（不等定时器）  ──▶ 时间戳 T_change
        │
        ▼
   Frame Scheduler 决定「这一帧值不值得编」
        │
        ├── 值得 → 送编码
        └── 不值得（低优先级/预算不足/重复帧）→ **不编码，也不补编**
```

**采集永远是事件驱动、立即执行；是否编码由调度器决定。** 这保证了「变化发生 → 采集」的 L1 ≤ 1 个 VSync（≤8ms@60Hz，≤4ms@120Hz）。

#### 关键补充（Q5）：无变化时不要重复编码

RustDesk 在捕获超时时对**同一份 YUV 重复编码最多 10 次**
（`src/server/video_service.rs:729` `repeat_encode_max = 10`，`:935`）。

这是纯浪费：画面没变，编出来的每一帧内容都一样，只是为了让码流「看起来活跃」。
在 60fps 下，若屏幕静止 1 秒，这会白烧 10 次编码 + 10 帧带宽。

**我们的要求（Q5）**：

| 情况 | 动作 |
|---|---|
| 捕获返回 `None`（无变化） | **什么都不做**，继续下一轮 |
| 对端需要保活 | 走**独立心跳**（控制通道），不占媒体通道 |
| 对端刚加入 | 发一次 IDR，之后按需 |
| 长时间静止后首次变化 | 正常编码，若非 IDR 则先发 IDR |

代价：某些老旧对端可能因长时间无帧而超时。我们的 `Transport` 有心跳机制覆盖这一点，
**不依赖媒体帧保活**。

## 3. 编码层（Encoder）

### 3.1 编码器选择策略

优先级（自动探测 + 可手动覆盖）：

| 平台 | 首选 | 次选 | 兜底 |
|---|---|---|---|
| Windows | NVENC (H.264/HEVC/AV1) | AMF (AMD) / QSV (Intel) | `openh264` 软件 |
| macOS | VideoToolbox H.264 | VideoToolbox HEVC | `openh264` |
| Linux | VAAPI (H.264) | NVENC | `openh264` |

**软件编码兜底要求**：1080p 必须能达到 30fps，否则该机器标为「不推荐使用」。

### 3.2 编码参数：延迟优先（关键）

这是「帧率上不去」的第二个源头：默认参数为质量优化，而非延迟优化。

| 参数 | 质量优先（错） | **延迟优先（RC 选择）** | 说明 |
|---|---|---|---|
| Preset | `slow`/`medium` | `p1`/`p4`（NVENC）、`speed`（VT）、`veryfast` | 单帧编码耗时 3–5× 差异 |
| B 帧 | 3–4 | **0** | B 帧引入重排序，至少 +1 帧延迟 |
| Look-ahead | 开 | **关** | 前瞻缓冲 = 固定延迟 |
| 码率控制 | VBR 2-pass | **CBR 或低延迟 VBR，单 pass** | 2-pass 需要整段缓冲 |
| 参考帧数 | 4–8 | **1–2** | 更多参考 = 更大重排 |
| 切片（slice） | 1 | **4–8 条** | 允许并行解码，降低解码延迟 |
| 熵编码 | CABAC 高压缩 | **CABAC 但禁用 trellis** | 折中 |
| 输出顺序 | 重排 | **零延迟（`NV_ENC_PIC_PARAMS::outputDelay=0`）** | 必须 |
| `infinity GOP` | 开（省码率） | **可控 GOP，关键帧按需** | 见 §3.3 |

参考基准（NVENC Turing+，1080p）：
- `p1` + B帧0 + CBR：单帧编码 **3–5ms**，可稳定 60fps 甚至 120fps
- `p7`（最高质量）+ B帧3：单帧编码 **15–25ms**，上限掉到 30fps

**这一项调整单独就能把帧率翻倍以上，且不增加任何带宽成本的上限。**

### 3.3 关键帧策略

| 场景 | 策略 |
|---|---|
| 会话开始 | 强制 IDR |
| 控制端上报丢包过多（连续 NACK 未恢复） | 强制 IDR |
| 新成员加入 | 强制 IDR |
| 定期刷新 | **禁用**；仅在「长 GOP 导致解码参考链断裂」时才刷新 |
| 画面剧变（场景切换检测） | 允许强制 IDR |

**不要定期强制关键帧** —— 每个 IDR 都是带宽尖峰（相当于 10–30 帧的码量），会导致瞬时拥塞 → 丢弃 → 画面卡一下。这是弱网卡顿的常见隐藏原因。

### 3.4 动态码率与分辨率

由拥塞控制反馈驱动（见 03 协议）：

```
拥塞信号（丢包率 / RTT / 带宽估计）
        │
        ▼
   Rate Controller
        │
        ├── 调整码率（首选，阶梯式）
        ├── 调整分辨率（次选，1080p → 900p → 720p）
        ├── 调整帧率（最后手段，60 → 45 → 30）
        └── 调整编码 preset（极端情况，质量换延迟）
```

**优先级原则：宁可降画质，不可降帧率。** 因为「卡顿」的主观印象远差于「模糊」。

例外：极端低带宽（<500kbps）下必须降帧率，否则每帧都是马赛克。

## 4. 帧调度器（Frame Scheduler）—— 本项目的核心创新点

### 4.1 为什么需要它

RustDesk 的帧率问题第三个源头：**没有 deadline-aware 调度**。

典型错误实现：

```
采集线程 → 无界队列 → 编码线程 → 无界队列 → 发送线程
```

一帧编码慢一点，队列就堆积；堆到 10 帧时，**你看到的画面比现实晚 166ms**；网络一卡，队列爆掉，然后**为了追上，瞬间发送大量帧**，把网络再打爆一次。

这就是「帧率上限高但实际很低」的真相：**不是编不出来，是排队的帧在互相挤压，最后被丢得七零八落。**

### 4.2 设计

```
                     ┌────────────────────────────────────┐
                     │      Frame Scheduler               │
                     │                                    │
  采集 ──────────────▶│  Priority Queue (按 deadline 排序) │
                     │                                    │
                     │  预算：≤ 2 帧在途                  │
                     │  超期策略：立即丢弃并请求关键帧     │
                     └──────────┬─────────────────────────┘
                                │
                                ▼
                            编码器
```

核心规则：

| 规则 | 说明 |
|---|---|
| **R1 在途帧上限 = 2** | 采集后最多 2 帧未完成发送。超过立即丢最旧帧 |
| **R2 deadline = 采集时刻 + 目标延迟** | 一帧若已超期，直接丢弃，不编码（省 CPU 也省带宽） |
| **R3 重复帧不编码** | `is_repeat` 或脏区为空 → 丢弃（静态画面零成本） |
| **R4 关键帧不可丢** | IDR 优先级最高，且为其预留带宽 |
| **R5 丢帧必须通知解码端** | 丢弃非 IDR 帧会导致参考链断裂 → 必须标记并要求关键帧 |
| **R6 编码器空闲时不投机编码** | 没有新内容就不编，不做「补帧」 |

### 4.3 调度器状态机（伪代码）

```rust
struct Scheduler {
    in_flight: ArrayDeque<InFlightFrame>,  // 最多 2
    target_latency: Duration,
    next_idr_deadline: Option<Instant>,
}

impl Scheduler {
    fn on_captured(&mut self, f: CapturedFrame) {
        // R3: 重复帧直接丢
        if f.is_repeat { return; }
        if f.dirty.is_some_and(|r| r.is_empty()) { return; }

        // R1: 挤出最旧帧
        while self.in_flight.len() >= MAX_IN_FLIGHT {
            let dropped = self.in_flight.pop_front();
            self.mark_broken(dropped);   // R5
        }

        // R2: 已超期不编
        let deadline = f.timestamp + self.target_latency;
        if Instant::now() >= deadline { return; }

        self.in_flight.push_back(InFlightFrame { f, deadline, .. });
    }

    /// 由编码器完成回调
    fn on_encoded(&mut self, seq: u64, bytes: Bytes) {
        debug_assert!(self.in_flight.front().map(|f| f.seq) == Some(seq));
        self.in_flight.pop_front();
        self.send(bytes);
    }
}
```

### 4.4 调度器的可观测性要求

**必须能回答「为什么这一帧没送到」**，否则无法诊断。

每帧记录一条结构化事件：

```rust
struct FrameTrace {
    seq: u64,
    t_captured: Instant,
    t_encode_start: Instant,
    t_encode_done: Instant,
    t_sent: Instant,
    t_acked: Option<Instant>,
    outcome: FrameOutcome,   // Delivered / DroppedRepeat / DroppedStale / DroppedBudget / LostInNetwork
}
```

会话结束后可导出「帧时间线」，用于离线分析。**这是产品能否持续优化的基础，第一版就要有。**

## 5. 解码与呈现层（Decoder / Renderer）

### 5.1 解码

| 要求 | 实现 |
|---|---|
| 硬件解码优先 | D3D11VA / VideoToolbox / VAAPI，直接输出 GPU 纹理 |
| 零拷贝呈现 | 解码纹理直接交给渲染器，禁止经 CPU |
| 低延迟模式 | 关闭解码器内部缓冲（`avcodec` 的 `flags2 = FAST`、`AV_CODEC_FLAG_LOW_DELAY`） |
| 输出顺序 | 因编码无 B 帧，解码可「进一出一」 |

### 5.2 抖动缓冲（Jitter Buffer）

**这里有个反直觉的关键点：远程桌面不应该有大抖动缓冲。**

与实时音视频不同，远程桌面的帧是「最新即最好」：晚到的帧通常没有价值（内容已经过时）。因此：

| 策略 | 说明 |
|---|---|
| 缓冲深度 = **0–2 帧（硬上限）** | 收到即解即显 |
| 不等待乱序帧 | 若第 N 帧未到但第 N+1 帧已到，**立即显示 N+1**（内容更新） |
| 但需参考链保护 | 若 N 是 IDR 则必须等；非 IDR 缺失则请求关键帧 |
| **队列满时丢最旧** | 绝不因队列满而阻塞接收 |

#### 为什么这里是 60 倍的差距（Q3）

RustDesk 的接收端队列是 **120 帧**（`src/client.rs:114` `VIDEO_QUEUE_SIZE = 120`）：

```
120 帧 ÷ 60fps = 2 秒缓冲
```

这意味着在最坏情况下，用户看到的画面比被控端真实屏幕**晚 2 秒**。
而且 RustDesk 自己知道这个队列污染了延迟测量（`video_qos.rs:43-44` 注释）：
TestDelay 探针与视频共享同一条流，测到的是「它前面的队列」，不是路径 RTT。

我们的要求：

```
2 帧 ÷ 60fps = 33ms 缓冲
```

**这是「画面比现实晚 2 秒」和「晚 33ms」的区别。** 用户感知上是「卡」和「不卡」的区别。

实现约束（写进 `rc-net` 与 `rc-decode`）：

| # | 约束 |
|---|---|
| 1 | 重组缓冲并发帧数硬上限 = 2（超出即丢最旧，记 `DroppedSuperseded`） |
| 2 | 解码队列深度硬上限 = 2 |
| 3 | 呈现队列深度 = 1（正在显示的那帧） |
| 4 | 任何一层队列满都**不得阻塞上游**，只能丢弃 |
| 5 | 延迟统计必须区分「路径延迟」与「排队延迟」，后者要从 RTT 反馈中扣除（Q6） |

**代价**：可能短暂显示错误画面（参考链断裂）。**缓解**：检测到断链立即请求 IDR，同时继续显示（宁可花屏 1 帧，不要冻结 50ms）。

### 5.3 呈现

| 要求 | 实现 |
|---|---|
| GPU 直通 | 解码纹理 → 渲染目标，用平台的零拷贝路径（D3D11 shared texture / IOSurface / dmabuf） |
| 缩放质量 | 双线性优先（`Linear`），高倍缩放用 `Lanczos`（GPU shader） |
| 垂直同步 | **关闭 vsync**（`Present(0)` / `CAMetalLayer.displaySyncEnabled=false`），否则每帧 +16.7ms |
| 撕裂处理 | 允许撕裂，用低延迟呈现模式 |
| 光标 | 本地光标优先（服务端发送光标位置+形状，控制端本地渲染，零延迟） |

**关闭 vsync 是延迟优化的经典必备项**，但会带来画面撕裂。考虑到远程桌面观感，撕裂可接受，冻结不可接受。

## 6. 输入通道（Input）

### 6.1 独立通道

```
控制端输入捕获 → 立即编码（<1ms）→ 高优先级 QUIC stream → 被控端注入
```

| 要求 | 说明 |
|---|---|
| 独立 stream | 与媒体流完全分离，不被视频帧阻塞 |
| 高优先级 | QUIC stream priority + 本地 socket 优先级（DSCP） |
| 小包合并 | 高频鼠标移动（125–1000Hz）需合并为 ~4ms 批次，避免包爆炸 |
| 绝对坐标 | 传归一化绝对坐标 + 分辨率，不传增量（避免漂移累积） |
| 乱序容忍 | 鼠标移动帧可丢弃旧值，键事件不可丢 |

### 6.2 本地回显

**用户判断「流畅」的主要依据是输入响应，不是画面帧率。**

| 要求 | 说明 |
|---|---|
| 光标本地渲染 | 控制端显示自己的鼠标指针（服务端发形状+热点），延迟感知为 0 |
| 输入指示 | 可选：显示「正在发送」的微动效 |
| 按键回显 | 可选的本地按键提示（远程协助场景） |

## 7. 延迟预算表（必须逐项兑现）

1080p60 局域网场景，单帧从「屏幕变化」到「上屏」：

| 阶段 | 预算 | 实测手段 | 超标应对 |
|---|---|---|---|
| 屏幕变化 → 采集返回 | 4ms | GPU 时间戳 / 事件回调时间 | 事件驱动改造 |
| 脏区分析 | 1ms | `Instant` 打点 | 降 tile 分辨率 |
| 调度器排队 | 0ms | 采样队列深度 | 减小在途上限 |
| 编码（NVENC p1，1080p） | 5ms | 编码器时间戳 | 降 preset / 降分辨率 |
| 打包 + FEC | 1ms | 打点 | 减少 FEC 开销 |
| 发送 → 接收（局域网） | 5ms | RTT/2 + 序列化 | pacing 优化 |
| 重组 + 抖动缓冲 | 1ms | 打点 | 缓冲深度=0 |
| 解码（硬件） | 3ms | 解码器时间戳 | 硬件解码 |
| 呈现（present） | 2ms | 打点 | 关闭 vsync |
| **合计** | **22ms** | | |

**预算 22ms，SLO 25ms（P50），留 3ms 余量。**

**回环模式（M1 Gate）不含「发送→接收」的 5ms 网络段，故其门槛为 18ms（22 − 5 + 1ms 余量）。** 这个换算关系必须保持：若后续调整网络段预算，M1 Gate 同步调整。

任何一项超标都必须在此表中记录并给出补偿方案。

## 8. 回环模式（Loopback Mode）—— 开发基础设施

**这是让 AI 能独立开发与验证的关键设计。**

```
┌────────────────── 同一个进程 ──────────────────┐
│                                                 │
│  Capture ──▶ Encode ──▶ [模拟网络损伤] ──▶ Decode ──▶ Render │
│                              │                              │
│                        可注入：丢包/延迟抖动/带宽限制        │
└─────────────────────────────────────────────────────────────┘
```

| 特性 | 说明 |
|---|---|
| 单机跑通全链路 | 不需要第二台机器 |
| 可注入网络损伤 | 模拟 3% 丢包、80ms RTT、抖动、限速 |
| 自动测量端到端延迟 | 屏幕注入测试图案 → 计时到收到该图案 |
| CI 可运行 | 无 GPU 时降级软件编码，仍验证逻辑正确性 |
| 生成帧时间线 | 供 AI 与人类共同诊断 |

**延迟的自动化测量方法**：在屏幕特定位置以 120Hz 闪烁编码的帧序号，通过回环解码读回该序号并与本地时钟比对。这是唯一能做到「glass-to-glass 自动测量」的实用方法，**必须在里程碑 M1 建立**。

## 10. 本文档的验收清单

架构层不通过以下任何一项，不进入功能开发：

### 通用指标

- [ ] 静态画面下 CPU 占用 ≤8% 单核（无变化则完全不采集）
- [ ] 1080p60 回环模式端到端延迟 ≤18ms（P50）（回环不含网络段：预算 22ms − 5ms 传输 = 17ms，留 1ms 余量）
- [ ] 每秒「采集帧数」与「编码帧数」不相等（证明重复帧被丢弃）
- [ ] 人为注入「编码器变慢」后，延迟不增长（证明调度器丢帧生效）
- [ ] 每帧可导出 `FrameTrace`，能回答「这帧为什么没到」
- [ ] 采集自愈清单（§2.5）10 项全部通过
- [ ] 关闭 vsync 后 present 延迟 ≤2ms
- [ ] 本地光标回显延迟感知为 0（拖动手感测试）

### Q1–Q6 专项（每项对应 RustDesk 的一个具体缺陷）

| # | 验收项 | 判定方法 | RustDesk 对照 |
|---|---|---|---|
| **Q1** | 连接后**首帧即达到目标帧率**，无冷启动降级 | 连接后 0.5 秒内 `Displayed FPS ≥ 目标 × 0.9` | 前 1 秒强制 15fps |
| **Q2** | 帧率调整**不依赖 1Hz 网络探针** | 断开网络探针（不注入延迟变化）后，本地 deadline 判定仍生效 | 依赖 1 秒周期的 TestDelay |
| **Q3** | 接收端任意一层队列**深度 ≤ 2 帧** | 单元测试断言队列上限；注入「呈现变慢」后队列不增长 | 120 帧 |
| **Q4** | 帧率升降**对称** | 从 15→60 与 60→15 用时比 ≤ 2:1 | 上升 +1/次，下降除法 |
| **Q5** | 静止画面**编码帧数 ≈ 0** | `--static-content` 跑 30s，`encoded_fps < 1` | 重复编码 10 次 |
| **Q6** | 延迟统计区分**路径延迟与排队延迟** | `FrameTrace` 中 `sched_queue` 与 `network` 分开统计，RTT 反馈不含排队 | 自认污染 |
