# 01 总纲：背景、目标与 SLO

## 1. 问题陈述

RustDesk 的帧率能力在参数上很漂亮（可配置到 60/120fps），但真实使用中：
- 静止画面尚可，**一动鼠标拖动窗口就明显掉帧、拖影、卡顿**
- 播放视频、滚动网页时**帧率降到 10–20fps**，观感像 PPT
- 弱网下画面**直接冻结数秒**，而不是降质降帧

用户感知到的是「帧率低」，但根因分散在采集、编码、调度、传输四层。**RC 的全部技术设计围绕「消除这条链路上的每一处帧率损失」展开。**

## 2. 目标（Goals）

### G1. 实际帧率达标的低延迟远程控制
- 1080p60 在局域网稳定跑满 60fps，端到端 ≤25ms
- 4K 场景有明确性能预算与降级策略（见 §4.3）
- **指标以「实际到达并呈现的帧」计算，不以「编码器输出的帧」计算**

### G2. 弱网不冻结
- 丢包 5% 时画面连续，允许画质下降但不允许冻结超过 200ms
- 无 TCP 队头阻塞；无重传等待导致的整屏停顿

### G3. 输入响应优先于画质
- 输入事件（键鼠）走独立高优先级通道，永不排队在视频帧之后
- 本地回显（cursor / 输入指示）保证操作手感

### G4. 跨三平台一致体验
- Windows / macOS / Linux 均支持硬件编码与原生采集
- 单一控制端可管理多台被控端

### G5. 安全默认开启
- 端到端加密，服务器无法看到画面内容
- 无密码直连需显式开启

### G6. AI 可持续开发
- 单文件改动的反馈回路 ≤3s（`cargo check`）
- 每个媒体层组件可在单机以「回环模式」自测，不依赖第二台设备

## 3. 非目标（Non-Goals）

明确不做，避免范围蔓延：

| 非目标 | 理由 |
|---|---|
| **文件传输 / 剪贴板大文件同步** | P1 之后；剪贴板文本 P0，大文件 P2 |
| **远程打印、远程音频（P2）** | 音频优先级低于视频；先保证视觉体验 |
| **多人同时观看/协作标注** | 会话模型第二阶段 |
| **浏览器 Web 客户端（第一版）** | `DecoderBackend` 预留 WASM 位置，但不在 P0 |
| **移动端（iOS/Android）** | P2 |
| **自建中继的完整运维体系** | 提供二进制与 Docker，不做多租户 SaaS |
| **穿透企业级防火墙 / 代理隧道** | 支持标准 QUIC/HTTP3，不做深度包伪装 |
| **支持 ARM 之外的冷门架构** | 支持 x86_64 + aarch64 |

## 4. SLO 定义

### 4.1 延迟的严格定义

**端到端延迟 = 被控端「屏幕内容发生变化」到「控制端屏幕上看到该变化」的时间（glass-to-glass）。**

分解为可独立测量的四段：

| 段 | 定义 | 上限（不得超出） | 实际分配（见 02 §7） |
|---|---|---|---|
| L1 采集延迟 | 屏幕变化 → 帧数据可读 | ≤ 8ms | 4ms |
| L2 编码延迟 | 帧进入编码器 → 码流可发 | ≤ 8ms | 6ms |
| L3 传输延迟 | 发出 → 收到完整帧 | ≤ 8ms（局域网） | 5ms |
| L4 解码+呈现 | 收到 → 上屏 | ≤ 6ms | 5ms |
| **合计** | | **≤ 30ms** | **22ms（P50 目标 25ms）** |

> 「上限」是任一段超出的红线，「实际分配」是 [02 架构 §7 延迟预算表](02-architecture.md) 的逐项拆解，含脏区分析、打包、重组等中间环节。

> 注意：L1 含「等待下一个采集周期」。60fps 下最坏要等 16.7ms，因此**采集不能是固定周期轮询**，必须由驱动/脏区事件驱动，否则 L1 下限就是 16.7ms。

### 4.2 帧率的严格定义

三种帧率必须分开统计，混用是 RustDesk 类产品误导用户的根源：

| 指标 | 定义 | 用途 |
|---|---|---|
| **Encoded FPS** | 编码器每秒输出的帧数 | 内部诊断 |
| **Delivered FPS** | 每秒完整送达控制端的帧数 | 内部诊断 |
| **Displayed FPS** | 每秒真正呈现到屏幕上的帧数 | **对外唯一指标** |
| **Perceived FPS** | 用户主观可感知的流畅度（需人工评分 + 滚动/拖动测试） | 验收 |

SLO 只对 **Displayed FPS** 与 **Perceived FPS** 负责。

### 4.3 SLO 矩阵

| 场景 | 分辨率 | 目标 Displayed FPS | 延迟 P50 | 延迟 P99 | 画质 |
|---|---|---|---|---|---|
| 局域网千兆 / 有线 | 1080p60 | 60 | ≤25ms | ≤40ms | 高质量 |
| 同城 Wi-Fi 6（RTT 20ms） | 1080p60 | ≥50 | ≤50ms | ≤80ms | 平衡 |
| 跨地域（RTT 80ms, 1% 丢包） | 1080p60 | ≥40 | ≤110ms | ≤180ms | 平衡 |
| 弱网（RTT 80ms, 3% 丢包） | 1080p | ≥30 | ≤150ms | ≤250ms | 降质保帧 |
| 4K 局域网 | 3840×2160 | ≥45 | ≤60ms | ≤100ms | 高质量 |
| 静态画面 | — | CPU ≤8%（单核） | — | — | — |

### 4.4 质量标准

| 指标 | 目标 |
|---|---|
| 画面冻结（>500ms 无更新） | 30 分钟会话内 0 次 |
| 会话中断率（非网络原因） | < 0.5% |
| 长时间会话（8h）内存增长 | < 5% |
| 冷启动到可连接（被控端） | < 1.5s |
| 首次画面出现（控制端点击连接后） | < 800ms |

## 5. 成功标准（Acceptance of the Product）

按重要性排序，前三项是「产品成立」的判据：

1. **主观流畅度优于 RustDesk**：同一网络、同一被控端，滚动长网页 + 拖动窗口，盲测中 RC 被选中 ≥70%
2. **1080p60 局域网延迟 ≤25ms（P50）**，且 `Displayed FPS` 与 `Encoded FPS` 差值 <5%
3. **3% 丢包下无冻结**，画面连续降级
4. 三平台均可用硬件编码，CPU 占用低于同场景 RustDesk
5. 静态画面 CPU 占用 ≤8% 单核

## 6. 用户角色与场景

| 角色 | 场景 | 关键需求 |
|---|---|---|
| 个人远程办公 | 家里连公司电脑，写代码、看文档 | 文字清晰、滚动流畅、输入无延迟 |
| IT 运维 | 批量管理服务器/办公机 | 多设备列表、批量操作、稳定不中断 |
| 技术支持 | 临时接入客户机 | 免安装、快速连接、文件传输 |
| 设计与剪辑 | 远程操作高分辨率屏幕 | 4K 支持、色彩准确、低延迟 |

## 7. 竞品定位

| 产品 | 优势 | 劣势（RC 的机会） |
|---|---|---|
| RustDesk | 开源、自建服务器、功能全 | **实际帧率低、弱网易冻结**、UI 粗糙 |
| AnyDesk | 延迟低、编解码自研 | 闭源、商用收费、自建不可 |
| Parsec | 游戏级延迟（<16ms） | 面向游戏、办公功能弱、需显卡 |
| TeamViewer | 功能全、企业生态 | 延迟高、价格贵、国内体验差 |

**RC 的差异化只有一个：在「办公/运维场景」做到接近 Parsec 的延迟表现。**

## 8. 技术假设与约束

| 项 | 假设 |
|---|---|
| 目标系统 | **macOS 13+（Apple Silicon，P0）**；Windows 10 2004+ / 11（P1）；Linux X11 + Wayland（P2） |
| CPU | x86_64 与 aarch64；硬件编码需 SSE4.2 / AVX2 或 NEON |
| GPU 编码可用性 | NVENC（GTX 10 系+）/ AMF（GCN+）/ QSV（6 代酷睿+）/ VideoToolbox（Apple Silicon & Intel）/ VAAPI（Mesa） |
| 网络 | 需要 UDP；QUIC 需可用（极少数网络禁 UDP，需 TCP 兜底降级） |
| 开发环境 | Rust stable，目标 3 个平台均可交叉编译或原生构建 |
| 团队 | 全部编码由 AI 完成，人类负责决策、验收与真机测试 |

## 9. 风险登记

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | DXGI/ScreenCaptureKit 的边界情况（换显示器、HDR、锁屏） | 黑屏、崩溃 | 采集器必须有「自愈重建」逻辑 + 集成测试清单 |
| R2 | Wayland 下的 dmabuf 路径复杂，不同合成器行为不一致 | Linux 体验差 | 优先 X11（XWayland 兼容），Wayland 作为 P1 |
| R3 | macOS 屏幕录制与辅助功能授权流程 | 无法安装使用 | 首个里程碑就打通签名与授权引导 |
| R4 | 硬件编码器驱动 bug（花屏、色彩偏差） | 画质事故 | 编码器自检 + 自动回退软件编码 + 颜色校验用例 |
| R5 | QUIC 在部分网络被限速/阻断 | 连不上 | 自研 TCP 隧道兜底（延迟差但可用） |
| R6 | AI 在 `unsafe` 边界写出隐蔽 bug | 运行时崩溃 | unsafe 隔离 + 单元测试 + 回环模式 + Miri/fuzz |
| R7 | 延迟预算分配不合理导致后期返工 | 进度 | 第一个里程碑就做端到端延迟埋点与测量 |
