# 03 协议、传输与安全

## 1. 传输层选型

### 1.1 决策：QUIC，不用 TCP，不用 WebRTC 默认栈

| 方案 | 优势 | 劣势 | 决策 |
|---|---|---|---|
| TCP + 自定义 | 穿透性好 | **队头阻塞**、无 FEC、拥塞控制不可控 | ❌ 禁用 |
| WebRTC（webrtc-rs） | 生态全、浏览器互通 | 依赖链重、定制受限、Rust 实现成熟度低 | ❌ P0 不用 |
| **QUIC（quinn）** | 无队头阻塞、内置 TLS1.3、连接迁移、可自定义 stream | 部分网络限制 UDP | ✅ **采用** |
| 裸 UDP | 最灵活 | 需自建加密与拥塞控制 | ❌ 重复造轮子 |

**理由**：媒体流需要「不重传的可靠」——丢包时宁可丢帧也不要等待。QUIC 的 datagram 扩展（RFC 9221）提供不可靠数据报，stream 提供可靠通道，两者可共存于一个连接、共享一次握手的拥塞控制与加密。

### 1.2 连接结构：双通道 + 单连接

```
QUIC Connection (TLS 1.3, 一次握手, 一次拥塞控制)
├── Stream A  (reliable, ordered)   控制通道：会话、鉴权、剪贴板、文件传输
├── Stream B  (reliable, ordered)   输入通道：键鼠事件（高优先级）
├── Stream C  (reliable, ordered)   IDR 帧通道（关键帧必须完整）
├── Datagram  (unreliable)          普通视频帧：丢即丢，永不重传
└── Datagram  (unreliable)          FEC 冗余包
```

**为什么不全部用 stream**：stream 保证有序可靠，丢一个包就要等重传，哪怕后面 5 个包都到了也交付不了 → 队头阻塞（表现为整屏冻结）。

**为什么不全部用 datagram**：IDR 帧丢了会导致解码器长时间花屏（参考链断裂），必须可靠送达。

### 1.3 拥塞控制

**决策：自定义（改造 BBR），不使用 quinn 默认的 BBR 或 CUBIC。**

原因：远程桌面的流量特征是「突发小包 + 长期中低速率 + 对延迟极度敏感」，通用拥塞控制（为吞吐优化）不合适。

| 需求 | 通用算法的问题 | RC 的做法 |
|---|---|---|
| 极低排队延迟 | BBR 会主动填充 buffer（pacing gain） | 限制 in-flight，目标 RTT ≤ 1.5× min RTT |
| 小包偏斜 | CUBIC 慢启动过冲 | 指数增长上限更保守 |
| 快速响应码率变化 | 探测周期慢 | 显式依赖「编码器码率」而非仅靠发送速率自适应 |
| 丢包不等于拥塞 | 无包恢复机制时会误判 | 结合 FEC 恢复率判断真实拥塞 |

**关键约束：发送侧的 pacing（平滑发送）必须实现。** 瞬间打满带宽会造成交换机/路由器缓冲膨胀 → RTT 尖峰 → 延迟抖动。这是「平均带宽够但卡顿」的常见根因。

```
pacing_rate = bps_estimate * 0.95
每个包在 pacing_timer 到期时发送（不能一轮发完）
```

### 1.4 序列化与协议格式

| 用途 | 格式 | 理由 |
|---|---|---|
| 控制消息（会话、鉴权） | protobuf | 跨语言（服务端可能是 Go）、可演进 |
| 媒体包头 | **手写二进制（固定布局）** | protobuf 解析开销 100ns+ 且难零拷贝；媒体包头必须 <1µs |
| 输入事件 | 手写二进制（位压缩） | 高频、小包、需极低开销 |

媒体包头设计（示例，每个 datagram-RTP 风格）：

```rust
#[repr(C)]
struct FrameHeader {
    magic: u32,          // 0x52_43_56_31 "RCV1"
    frame_seq: u64,      // 帧序号
    packet_idx: u16,     // 该帧内包序号
    packet_cnt: u16,     // 该帧总包数
    fec_group: u16,      // FEC 组号
    flags: u8,           // bit0=IDR, bit1=last_packet, bit2=has_dirty_region
    layer_id: u8,        // 可分层预留
    capture_ts_us: u32,  // 采集时刻（相对会话开始，微秒）
    encode_done_us: u32, // 编码完成时刻
    payload_len: u16,
}
// 16 + 4 + 4 = 24 字节，无 varint，无分支解析
```

**包头必须携带时间戳**：控制端用它在同一次网络条件下推算每一段的耗时，实现端到端延迟的在线归因。

## 2. FEC 与重传策略

### 2.1 分层可靠性

| 数据 | 丢失后果 | 策略 |
|---|---|---|
| 输入事件 | 键卡住 / 鼠标错位 | **可靠 stream + 重传** |
| 控制消息 | 会话状态不一致 | 可靠 stream |
| IDR 帧 | 长期花屏 | 可靠 stream（或 datagram + NACK 强重传） |
| P 帧 | 短暂花屏 / 参考链断裂 | **datagram + FEC，不重传** |
| 光标形状 | 光标不更新 | 可靠 stream |

### 2.2 FEC 方案

**使用 XOR 块 FEC（类似 WebRTC 的 `ulpfec`），而非 Reed-Solomon。**

| 方案 | 优缺点 |
|---|---|
| XOR 块 FEC | 开销低、实现简单、延迟为 0（解码在收齐组内包后立即完成）；恢复能力有限（每块恢复 1 个丢包） |
| Reed-Solomon | 恢复能力强（可恢复 k 个），但编解码有 CPU 成本，且需要更长块 |
| 自适应 | P0 只做 XOR + 自适应冗余率，P1 再考虑 RS |

自适应冗余率：

```
收到 NACK / 观察到丢包率 p
冗余率 r = clamp(p * 1.5, 0, 0.3)     // 丢包 10% → 冗余 15%
冗余包在帧的最后一个包发送后立即发出（不等下一帧）
```

**关键：FEC 包必须与数据包在同一个 pacing 窗口内发送**，否则等于把延迟转成了冗余。

### 2.3 NACK 策略

| 条件 | 动作 |
|---|---|
| 发现 P 帧缺包 | 发送 NACK（批量，一次最多 32 个 seq） |
| NACK 后 1 个 RTT 仍未恢复 | 放弃该帧，**立即请求 IDR** |
| 连续 3 帧参考链断裂 | 强制 IDR |
| IDR 丢失 | 可靠通道，重传至成功 |

**禁止无限重传 P 帧** —— 这是「画面冻结」的直接原因。等一个已经过时的帧没有任何价值。

## 3. 连接建立与 NAT 穿透

### 3.1 三条连接路径

```
1. 直连（同局域网 / 公网可路由）
   Host ←── QUIC ──→ Controller         延迟最低，优先尝试

2. UDP 打洞（双方在 NAT 后）
   Host ←→ Rendezvous Server ←→ Controller
   双方各自向对方公网地址发 UDP → 建立直连

3. 中继（打洞失败）
   Host ←→ Relay Server ←→ Controller    延迟 +RTT，但可用
```

### 3.2 连接流程

```
Controller                    Rendezvous                    Host
    │                              │                          │
    │──1. 登录/查询设备ID──────────▶│                          │
    │                              │◀─── 心跳（公网地址）─────│
    │◀─2. 返回 Host 候选地址列表───│                          │
    │                              │                          │
    │──3. 并行打洞（同时向候选地址发 QUIC Initial）──────────▶│
    │◀─────────────────────────────────────── 握手成功 ───────│
    │                              │                          │
    │──4. 鉴权（密钥交换 / 密码 / 二次确认）─────────────────▶│
    │◀─────────────────────────────────────── 会话建立 ───────│
    │                              │                          │
    │◀═══════════ 5. 媒体流 + 输入流 ════════════════════════▶│
```

| 步骤 | 超时 | 失败动作 |
|---|---|---|
| 候选地址获取 | 2s | 直接用中继 |
| 打洞（每地址并行） | 3s | 回退中继 |
| 握手 | 5s | 重试 1 次 → 报错 |
| 鉴权 | 30s（等用户确认） | 超时断开 |

### 3.3 Rendezvous 服务最小设计

| 职责 | 说明 |
|---|---|
| 设备注册 | 设备 ID（公钥指纹）+ 在线状态 |
| 地址分发 | 返回公网地址 + 内网地址列表 |
| 中继协调 | 分配 relay 资源 |
| **不做** | **不转发、不存储、不解密任何会话内容** |

**安全边界：rendezvous 服务器是零知识设计**——即使服务器完全被攻破，攻击者也无法查看任何会话画面。这既是安全特性，也是信任卖点。

## 4. 安全设计

### 4.1 威胁模型

| 威胁 | 攻击者能力 | 防护 |
|---|---|---|
| 窃听 | 网络中间人 | QUIC 内置 TLS 1.3，前向保密 |
| 中间人替换 | 篡改 rendezvous 返回值 | 设备身份基于公钥指纹，控制端校验指纹（首次确认 + TOFU） |
| 未授权连接 | 知道设备 ID | 密码 / 临时令牌 / 二次确认，默认不接受免密 |
| 服务器被攻陷 | 完全控制 rendezvous | 端到端加密，服务器零知识 |
| 重放攻击 | 录制并重放握手 | TLS 1.3 nonce + 会话随机数 |
| 恶意被控端 | 被控端是攻击者 | 控制端也验证被控端身份；只读模式 |
| 剪贴板/文件窃取 | 恶意操作 | 权限分级、剪贴板需显式授权 |

### 4.2 身份与鉴权

**设备身份 = Ed25519 密钥对**

- 首次启动生成密钥对，私钥存于平台密钥库（Windows DPAPI / macOS Keychain / Linux Secret Service）
- 设备 ID = 公钥的短哈希（如 9 位 Base32），人类可读、可校验
- 会话密钥由双方临时生成（X25519 ECDH），**TLS 之上再做一次端到端加密层**（防止中继或服务器解密）

**为什么 TLS 之上还要 E2E**：TLS 终止于中继服务器（若走中继），此时 TLS 只保护到服务器。E2E 层保证即使服务器被控制也无法解密。

```
TLS 1.3 (transport)  ← 保护到中继服务器
  └── X25519 + ChaCha20-Poly1305 (session)  ← 保护到对端
```

### 4.3 访问控制模型

| 模式 | 说明 | 默认 |
|---|---|---|
| 密码验证 | 固定密码或一次性密码 | ✅ 启用 |
| 临时令牌 | 生成有时效的连接码 | ✅ 可用 |
| 二次确认 | 被控端弹窗，用户点「接受」 | ✅ 默认 |
| 免密直连（白名单） | 指定设备 ID 直接连接 | ❌ 默认关闭 |
| 只读模式 | 仅观看，不注入输入 | ✅ 可选 |
| 权限细分 | 剪贴板 / 文件 / 音频 / 输入 独立开关 | ✅ 可选 |

## 5. 协议演进与兼容

| 要求 | 规则 |
|---|---|
| 版本协商 | 握手时交换 `proto_version: u16`（major.minor 打包） |
| minor 兼容 | 新增字段必须可选，旧端忽略 |
| major 不兼容 | 明确拒绝并提示升级，不做「尽力兼容」 |
| 能力协商 | 独立的 `Capability` 位图（H264/HEVC/AV1/多显示器/文件传输…） |
| 扩展字段 | protobuf 的 `reserved` 与 `unknown fields` 保留 |

## 6. 性能约束与实现注意事项

| 约束 | 数值 | 理由 |
|---|---|---|
| 媒体包头解析 | ≤ 200ns | 每帧可能几十个包，累计不可忽略 |
| 单个 datagram 大小 | 1200–1400 字节 | 避免 IP 分片（分片丢失 = 整包丢失） |
| 编码后一帧的包数 | 1080p ≈ 10–40 包 | 影响 FEC 块大小选择 |
| NACK 批处理 | 每次最多 32 seq，最小间隔 5ms | 防 NACK 风暴 |
| 控制消息最大尺寸 | 1MB（分块） | 防内存攻击 |
| 零拷贝要求 | 从编码器输出到 socket 写入必须零拷贝 | 用 `Bytes` / `IoSlice` |
| 每连接内存上限 | 16MB | 多连接场景防 OOM |

## 7. 服务端需求（最小可用）

| 组件 | 功能 | 部署 |
|---|---|---|
| Rendezvous | 设备注册、地址分发、中继协调 | 单二进制 + Docker |
| Relay | 转发 QUIC 数据（不解密） | 单二进制，可水平扩展 |
| API | 设备管理、用户认证、审计查询（可选） | 单二进制 |

**服务端不需要在第一里程碑实现**：M1–M3 用「固定地址 + 由用户输入 IP」直连即可完成全部延迟验证。

## 8. 本文档的验收清单

- [ ] 3% 丢包下，画面连续（无 >500ms 冻结），帧率 ≥30
- [ ] 10% 丢包下，仍可辨识画面内容，帧率 ≥15（降级而非冻结）
- [ ] 打洞成功率 >70%（典型家用 NAT）
- [ ] 打洞失败后 3 秒内自动切到中继，用户无感知
- [ ] 中继场景延迟 = 直连延迟 + RTT（差值 ≤ 1.2 × RTT）
- [ ] 一次握手的连接建立时间 ≤300ms（局域网）
- [ ] 网络切换（Wi-Fi → 有线）后连接不中断（QUIC 连接迁移）
- [ ] 抓包验证：服务器侧无法还原画面
- [ ] 控制消息与媒体流共享连接时，媒体流量不影响输入延迟（输入 P99 ≤ RTT + 5ms）
